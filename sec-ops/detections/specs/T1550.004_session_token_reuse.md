# Detection Spec — Session Token Reuse From Multiple Locations / Browsers

**ID:** `PL-DET-0008`
**Technique:** T1550.004 — Use Alternate Authentication Material: Web Session Cookie
**Related:** T1539 (Steal Web Session Cookie), T1078 (Valid Accounts), T1557 (AiTM)
**Tactic:** Defense Evasion (TA0005), Credential Access (TA0006), Initial Access (TA0001)
**Author:** Keith M · **Version:** 1.1 · **Date:** 2026-07-24 · **Updated:** 2026-07-28
**Status:** experimental — thresholds require baselining before production

---

## 1. What this actually detects

One session token presented from two or more distinct browsers, from distinct
network locations, inside a short window.

The critical insight — and the reason this detection is worth building at all:

> **A session cookie cannot legitimately move between browsers.**
> Chrome does not share cookie jars with Safari or Firefox. If the same session
> identifier arrives from Chrome/Windows and Safari/macOS, either the token was
> exported from the browser's cookie store, or it was intercepted in transit.
> There is no benign path that produces this.

Geography is the *weaker* signal and should never be the primary condition.
VPNs, corporate egress, mobile carrier IP rotation and Apple iCloud Private Relay
all move a user across the map legitimately, many times a day. Browser identity
does not move. **Build the alert on the browser mismatch and use geography only
to escalate.**

This detection is the primary post-compromise catch for adversary-in-the-middle
phishing (Evilginx, Modlishka, EvilProxy), infostealer cookie theft (Lumma,
RedLine, Raccoon), and token replay following an OAuth consent attack — all of
which bypass MFA entirely, because the stolen token is *already authenticated*.
MFA does not help here. This alert is what catches it.

## 2. Alert conditions

### 2.1 Required — ALL must be true

| # | Condition | Rationale |
|---|---|---|
| **R1** | Same session identifier across ≥2 events | The join key. Entra `SessionId`, Okta `externalSessionId`, or a **salted hash** of the app's session cookie / JWT `jti`. |
| **R2** | Same user principal | Guards against session-ID collisions across tenants or apps. |
| **R3** | ≥2 distinct **normalised** browser fingerprints | See §3 — normalisation is mandatory, raw User-Agent inequality is unusable. |
| **R4** | ≥2 distinct source IPs in **different /24 AND different ASN** | Same-ASN movement is usually one org's egress pool or one carrier. |
| **R5** | Both observations within the correlation window | Default **60 minutes**. Widen to 24h for a lower-severity hunt. |
| **R6** | No suppression condition in §2.3 matches | |

R3 and R4 together are the alert. Either alone is noise.

### 2.2 Escalation — any raises severity

| # | Condition | Effect |
|---|---|---|
| **E1** | Impossible travel: implied velocity **> 900 km/h** | High → Critical |
| **E2** | Different country | +1 tier |
| **E3** | **Interleaved** activity (A→B→A), not merely sequential | +1 tier — near-proof of concurrent use |
| **E4** | Account holds a privileged role | +1 tier |
| **E5** | One IP on a hosting, VPN, Tor or anonymiser ASN | +1 tier |
| **E6** | Session continued **without re-authentication or MFA re-prompt** | +1 tier — hallmark of replay rather than a genuine new sign-in |
| **E7** | **JA3/JA4 TLS fingerprint mismatch while User-Agent matches** | +2 tiers — see §3.3 |
| **E8** | Okta `dtHash` / Entra `DeviceDetail.deviceId` changed mid-session | +1 tier |

### 2.3 Suppression — alert must NOT fire if any match

| # | Condition | Why |
|---|---|---|
| **S1** | Both IPs within known corporate egress ranges | Split-tunnel and multi-site NAT |
| **S2** | Both IPs on the same **mobile carrier** ASN | Phones rotate IPs constantly, including across cities |
| **S3** | Either IP on **Apple iCloud Private Relay** egress | Relay egress relocates the user by design; publish list refreshed weekly |
| **S4** | Browser difference is **version-only** within the same family | Auto-update mid-session is extremely common — this is the #1 false positive |
| **S5** | User-Agent belongs to a known background/sync service or app-embedded webview | Outlook, Teams, OneDrive and native app webviews reuse tokens by design |
| **S6** | Session identifier is a long-lived refresh/service token, not an interactive session | Different lifecycle entirely |
| **S7** | User is on the approved-travel or VPN-exception list | Feed from HR/IT if available |

**S4 is the one that will hurt you if you skip it.** An unnormalised
`user_agent != user_agent` comparison alerts every time Chrome auto-updates
mid-session, which is daily, across the whole estate.

### 2.4 Severity matrix

| Browser family | Country | Window | Severity |
|---|---|---|---|
| Same | Different | ≤60m | **Low** — investigate as VPN/relay first |
| Different | Same | ≤60m | **Medium** |
| Different | Different | ≤60m | **High** |
| Different | Different + E1 or E3 | ≤60m | **Critical** |
| Different | any + E7 | any | **Critical** |

## 3. Normalisation — mandatory pre-processing

### 3.1 Browser fingerprint

Reduce the User-Agent to `family|major_version_bucket|os_family`, then compare
**family and OS only** for R3:

```
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ... Chrome/126.0.0.0
  →  chrome|126|windows
Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ... Version/17.5 Safari/605.1.15
  →  safari|17|macos
```

`chrome|126|windows` vs `chrome|127|windows` → **same family, suppress (S4)**.
`chrome|126|windows` vs `safari|17|macos` → **different family, R3 satisfied**.

### 3.2 Never log raw tokens

Session cookies and JWTs are credentials. Logging them raw turns your SIEM into
a credential store and your detection engineers into an insider-threat surface.
Hash with a keyed HMAC before indexing:

```
session_key = HMAC-SHA256(key = <siem_pepper>, msg = <raw_cookie_or_jti>)
```

The detection only ever needs equality, never the plaintext.

### 3.3 Prefer JA3/JA4 over User-Agent

User-Agent is a client-supplied string and trivially spoofed — a competent
attacker replaying a stolen cookie copies the victim's UA verbatim, defeating R3.
JA3/JA4 fingerprints the TLS ClientHello (cipher suites, extensions, curves),
which is a property of the attacker's actual TLS stack and far harder to forge.

Therefore:

- **UA differs, JA3 differs** → unsophisticated replay. Caught by R3.
- **UA matches, JA3 differs** → *deliberate* UA spoofing. **Stronger signal, not weaker** (E7).
- **UA differs, JA3 matches** → likely the same client; check for a browser update (S4).

Available only where you terminate TLS yourself (§4.3). Where you have it, make
JA4 the primary R3 input and demote UA to corroboration.

## 4. Field mappings

### 4.1 Entra ID / Azure AD — `SigninLogs`

| Concept | Field |
|---|---|
| Session ID | `SessionId` |
| User | `UserPrincipalName` |
| Source IP | `IPAddress` |
| Geo | `LocationDetails.geoCoordinates.{latitude,longitude}`, `.countryOrRegion`, `.city` |
| Browser | `DeviceDetail.browser` |
| OS | `DeviceDetail.operatingSystem` |
| **Client app** | `clientAppUsed` |
| Device | `DeviceDetail.deviceId`, `.trustType` |
| ASN | `AutonomousSystemNumber` |
| Re-auth | `AuthenticationRequirement`, `ConditionalAccessStatus` |
| Risk | `RiskLevelDuringSignIn`, `RiskState` |

Entra populates `DeviceDetail.browser` as e.g. `Chrome 126.0.0`, so split on the
first space for family. Enable **Continuous Access Evaluation** — it revokes
tokens on IP change and is the control that makes this detection actionable.

**Scope to browser sign-ins with `clientAppUsed`, not `DeviceDetail.browser`.**
The non-browser client types — `Mobile Apps and Desktop clients`, `Exchange
ActiveSync`, `IMAP4`, `POP3`, `MAPI`, `Other clients` — are values of
`clientAppUsed`. They never appear in `DeviceDetail.browser` (which holds only a
browser name), so a filter that excludes them by matching the browser field
matches nothing and excludes nothing. Filter non-interactive clients on
`clientAppUsed`, and drop events with a null `DeviceDetail.browser` so they
cannot inflate the distinct-browser count (R3).

### 4.2 Okta — System Log

| Concept | Field |
|---|---|
| Session ID | `authenticationContext.externalSessionId` |
| User | `actor.alternateId` |
| Source IP | `client.ipAddress` |
| Geo | `client.geographicalContext.{country,city,geolocation.{lat,lon}}` |
| Browser | `client.userAgent.browser` |
| OS | `client.userAgent.os` |
| Raw UA | `client.userAgent.rawUserAgent` |
| ASN | `securityContext.asNumber`, `securityContext.isProxy` |
| **Device token** | `debugContext.debugData.dtHash` |

`dtHash` is Okta's device token. A change in `dtHash` while `externalSessionId`
stays constant is one of the cleanest hijack signals available in any product —
weight it heavily (E8).

### 4.3 Lab web app + reverse proxy (Juice Shop / flask-sqli behind nginx or Traefik)

Log format to emit — note the cookie is **hashed at the proxy**, never indexed raw:

```
$remote_addr $ssl_ja4 "$http_user_agent" "$request" $status
  session=$hashed_session_cookie geo=$geoip2_data_country_code
```

| Concept | Field |
|---|---|
| Session ID | `session_key` (HMAC of `connect.sid` / `JSESSIONID` / JWT `jti`) |
| User | `user.name` (from app log, joined on session) |
| Source IP | `source.ip` |
| Geo | GeoIP enrichment at index time |
| Browser | `user_agent.name`, `user_agent.os.name` (parsed) |
| **TLS fingerprint** | `tls.client.ja3` / `tls.client.ja4` |

This is the reproducible version — no cloud tenant required. It is also the only
one of the four with JA3/JA4, so use it to validate the E7 logic.

### 4.4 Generic / Splunk CIM

Datamodels `Authentication` and `Web`: `user`, `src`, `http_user_agent`,
`session_id`, `src_country`, `action`. Least precise; map per-source.

## 5. False positive model

| Scenario | Frequency | Handled by |
|---|---|---|
| Browser auto-update mid-session | **Very high** | S4 + §3.1 |
| Corporate VPN split-tunnel | High | S1 |
| Mobile carrier IP rotation | High | S2 |
| iCloud Private Relay | Medium | S3 |
| Native app webview reusing token | Medium | S5 |
| User genuinely on two devices | Medium | R1 — separate devices get separate sessions; if not, that's an app bug worth finding |
| Legitimate air travel | Low | E1 velocity, plus S7 |

Expect the first tuning pass to be dominated by S4 and S5. Baseline for two
weeks in monitor-only mode before enabling notable/alert actions.

## 6. Response

1. **Revoke the session** — this is the only action that matters, and it must be
   first. Entra: `Revoke-MgUserSignInSession`. Okta: clear user sessions via API.
   Password reset alone does **not** invalidate an existing session token.
2. Force re-authentication with MFA.
3. Identify the theft vector: infostealer on the endpoint (correlate with the
   T1003.001 and C2 detections in this repo), or an AiTM proxy — check for a
   preceding sign-in from a hosting ASN.
4. If infostealer is suspected, treat **every** browser-stored credential and
   cookie on that host as compromised, not just this session.
5. Hunt the same `session_key` and source IP across all other users.

---

## 7. Validation in this lab

1. Authenticate to Juice Shop from Firefox on the Kali attack VM.
2. Extract the `connect.sid` cookie from devtools.
3. Replay it from Chrome on a Windows endpoint on a different VLAN:
   `curl -H "Cookie: connect.sid=<value>" https://juice.lab.local/rest/user/whoami`
4. Confirm R1–R5 all satisfy and the alert fires at High.
5. Repeat with a spoofed matching User-Agent to confirm E7 (JA4 mismatch) still
   catches it where R3 alone would not.
6. Negative test: repeat from the same browser after forcing an update — confirm
   S4 suppresses.
